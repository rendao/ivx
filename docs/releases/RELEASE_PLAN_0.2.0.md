# IVX 0.2.0 功能升级与版本发布计划（稳定性里程碑）

## 1. 发布目标
- 版本目标：0.2.0
- 主目标：把当前可用的看板能力升级为可持续运行、可追踪、可回滚的稳定版本。
- 原则：稳定性优先于功能扩张；先把单项目运行链路做深做稳，再扩展多项目能力。

## 2. 本次升级范围（必须完成）

### A. 数据契约与输入健壮性
- 为 POST /api/progress 增加严格字段校验与错误响应规范。
- 对关键字段做边界保护（百分比、枚举值、空值处理）。
- 为 push 脚本增加输入前置校验与错误提示一致性。

验收标准：
- 非法 payload 返回 400，且包含可读的错误说明。
- 三个 push 脚本在异常参数下都能输出明确失败原因并以非 0 退出。

### B. 状态文件可靠性
- 对 data/live_progress.json 与项目级状态文件采用原子写入策略。
- 增加启动时损坏恢复机制（回退到最近可用快照或默认合同）。
- 增加最小化轮转备份（例如最近 3 份）。

验收标准：
- 模拟中断写入后，服务重启不崩溃，仍可提供可用默认状态。
- 状态文件可持续读写 24 小时不出现不可恢复损坏。

### C. 可观测性与运行诊断
- 增加健康检查端点（例如 /api/health）。
- 对关键路径增加结构化日志字段（时间、项目、事件类型、结果）。
- 明确 debug 日志开关行为并补充文档。

验收标准：
- 通过 health 端点可区分服务正常、数据文件异常、项目路径异常。
- 异常场景能在日志中定位到请求和失败点。

### D. 发布与安装可用性
- 增加最小 smoke 测试脚本（安装、启动、推送、读回）。
- 补齐版本发布清单：版本号、变更记录、tag、回滚说明。
- 对 README 与 README_ZH 的命令、端口、入口进行一致性核对。

验收标准：
- 在全新环境中，按文档 10 分钟内完成安装并看到看板数据更新。
- 版本包可通过 pip install ivx==0.2.0 安装并运行。

## 3. 本次明确不做（延后到 0.3.x）
- 多租户权限体系。
- 复杂前端重构与视觉大改版。
- 非 Python 技术栈的深度 SDK 支持。

## 4. 里程碑与时间表（建议 2 周）

### M1：稳定性改造（D1-D4）
- 完成输入校验、原子写入、恢复机制设计与实现。
- 提交单元验证与异常场景脚本。

### M2：可观测性与文档对齐（D5-D7）
- 增加 health 端点和关键日志字段。
- 完成中英文文档一致性修订。

### M3：发布候选（D8-D10）
- 执行 smoke 测试与手工回归。
- 产出 RC 版本（0.2.0-rc1）。

### M4：正式发布（D11-D14）
- 修复 RC 问题并冻结变更。
- 发布 0.2.0，打 tag，生成发布说明。

## 5. 发布执行清单（单一路径）
1. 功能冻结：仅允许 P0/P1 缺陷修复进入发布分支。
2. 版本更新：pyproject.toml 从 0.1.0 升级到 0.2.0。
3. 测试通过：
   - 启动服务
   - push_live_progress.py 推送成功
   - push_collaborator_update.py 推送成功
   - push_ci_result.py 推送成功
   - API 读回关键字段正确
4. 文档更新：README.md、README_ZH.md、HANDOVER.md 更新版本与发布说明入口。
5. 打 tag：v0.2.0。
6. 发布包并安装验证。
7. 发布后监控 24 小时，确认无 P0 故障。

## 6. 风险与回滚预案
- 风险 1：状态文件升级导致兼容问题。
  - 预案：保留旧格式读取兼容层；发布前自动备份 data/。
- 风险 2：输入校验过严导致现有推送中断。
  - 预案：先发告警日志模式，再切换为强校验；保留降级开关。
- 风险 3：发布后环境差异导致无法启动。
  - 预案：保留 0.1.0 安装指令与回滚脚本，30 分钟内可回退。

## 7. 角色与责任
- Product owner：定义 0.2.0 范围与验收。
- Tech owner：推进稳定性改造、质量门禁与发布把关。
- Release owner：执行版本打包、发布、tag 与回滚预案。

## 8. 完成定义（Definition of Done）
- 0.2.0 所有必须范围验收通过。
- 关键链路连续运行验证通过（至少 24 小时）。
- 发布文档、变更记录、回滚说明齐备。
- 用户可按 README 命令独立完成安装、启动、推送和查看。
